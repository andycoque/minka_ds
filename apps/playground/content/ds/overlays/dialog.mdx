## Anatomy

<DialogDemo />

Two props carry most of the behaviour and neither is obvious from the name.

`flow` caps the dialog at `calc(100dvh - 12.5rem)` and lays the children out as a
flex column with `min-h-0`, so an inner `flex-1 overflow-y-auto` region scrolls
instead of the box growing past the screen. Short dialogs are unaffected: they
still shrink-wrap under the cap. Any dialog with a form in it wants this.

`DialogPanel` adds a context column beside the body, for the thing being acted on.
`placement="side"` puts it left; `inset` floats it with an 8px frame instead of
bleeding to the dialog edge.

## Variants

Dialog has no `variant` prop. What changes is the width, set with a class on
`DialogContent`.

| Width | Use |
| --- | --- |
| `max-w-md` | A confirmation, or two or three fields. |
| `sm:max-w-3xl` | A form with a panel beside it. |
| default | Everything else. |

## Left panel

<DialogPanelDemo />

`DialogPanel` turns a dialog into two columns: the panel holds **what is being acted
on**, the body holds **the decision**. Ten studio dialogs use one.

Its purpose is to stop a reader losing the object while they act on it. A status change
dialog that only shows a list of states asks "which state?" without saying "for what" —
the panel answers the second question so the body only has to ask the first.

### What it holds

Three things, in the product:

- **The object itself.** An object card, a resolution diagram, a live preview of what is
  being created. This is the common case and the reason the panel exists.
- **A help expander**, `inset` and anchored bottom-right, filling the space below the
  object. This is the only place `inset` works — see
  [Help expander](/docs/ds/surfaces/help-expander).
- **An alert**, for a consequence that belongs with the object rather than beside the
  button that triggers it.

### Examples

The creation wizards each show a live card of the record being built, so a reader can
see the object take shape as they fill the form. The
[status change dialog](/docs/ds/detail-pages/status-change-dialog) shows the record's
card plus the consequence of the selected state. The liquidity movement dialogs show a
[flow diagram](/docs/ds/diagrams/flow-diagram) with the balances before and after.

The pattern in all three: **the body is where you decide, the panel is what you are
deciding about.**

## Motion

Shown as a loop on an abstract block rather than on a dialog. A specimen shows what a
dialog looks like; a loop shows what the movement feels like, and stripping the chrome
leaves only the thing being documented.

<DialogMotionLoop />

Two layers on offset timings. Going in, the backdrop leads and the card follows 60ms
behind, so the surface arrives before the content. Coming out it inverts: the card leaves
first and the dim lingers 100ms, so it does not snap away from under a departing card.

The asymmetry is deliberate. Arriving settles over 500ms on a soft curve; leaving gets out
of the way in 300ms on an ease-in. Arriving deserves attention, leaving does not.

The keyframes live in the component rather than as Tailwind utilities, because Radix
unmounts the node before a utility-driven exit animation can play.

## Use something else when

- **The flow has ordered steps.** `Wizard`, which owns the stepped body, the
  footer and the discard guard.
- **The content is a side surface, not a decision.** `Sheet`, which slides from an
  edge and leaves the page visible behind it.
- **It is a short confirmation attached to a control.** `Popover` if it can be
  dismissed by clicking away, since a dialog takes the whole screen to ask.
- **It is only feedback.** `toast`. A dialog demands an action; feedback does not.

## Do and don't

<DoDont>
  <Rule>
    <Do>
      Pass `flow` on any dialog with a form, so the body scrolls and the footer
      stays reachable.
    </Do>
    <Dont>
      Let a long dialog grow past the viewport. The actions end up below the fold
      with nothing to scroll.
    </Dont>
  </Rule>
  <Rule>
    <Do>
      Name the action in the title and repeat it on the primary button: "Revoke
      API key", then "Revoke".
    </Do>
    <Dont>
      Title it "Are you sure?" and label the button "Yes". Neither says what
      happens.
    </Dont>
  </Rule>
  <Rule>
    <Do>
      Use `DialogPanel` to keep the thing being acted on visible while the reader
      decides.
    </Do>
    <Dont>
      Restate the record as prose in the body. The panel exists so the decision
      and its subject share the screen.
    </Dont>
  </Rule>
</DoDont>

## Props

<PropsTable>
  <Prop name="flow" type="boolean" default="false">
    Caps the height and makes the children a scrolling flex column. Pair it with
    `flex-1 overflow-y-auto` on the region that should scroll.
  </Prop>
  <Prop name="open / onOpenChange" type="boolean / (open: boolean) => void">
    Controlled pair. Omit both to let `DialogTrigger` manage it.
  </Prop>
  <Prop name="DialogPanel placement" type="'side' | 'top'" default="'side'">
    Where the panel sits. `side` takes two fifths of the width; `top` runs across
    the head of the dialog.
  </Prop>
  <Prop name="DialogPanel inset" type="boolean" default="false">
    Floats the panel with an 8px frame instead of bleeding to the dialog edge.
  </Prop>
  <Prop name="showCloseButton" type="boolean" default="true">
    The X in the corner. Turn it off when the dialog must be resolved by an
    action.
  </Prop>
</PropsTable>
